# M21 — A session can finish

Six commits on `m21-session-finish`. Decided by [ADR-0020](../adr/0020-session-finish.md), the
second of the two engine changes [ADR-0018](../adr/0018-chess-probe.md) said chess would force.

## What this milestone was for

A lockstep session ended five ways and every one was a failure. A peer that chose to leave sent
a goodbye its partner reported as an error. The lab lived with that since M17: its socket peer
ran to `--ticks`, printed its hash and returned, and its partner learned the run was over from
the socket closing — which it could notice before applying the last turns that arrived with the
close. M17 narrowed that window by draining what was queued. It could not close it, because
nothing in the protocol said *"I am done at tick T"*.

Chess cannot live with it. A game ends at checkmate, at the same tick on every peer, and both
players' processes should exit zero having agreed on the whole game.

## The design, and where it differs from the plan

**A new message, `Finish{last_tick}`, and protocol version 2.** The plan sketched a goodbye with a
new reason. That was wrong: every handler of a goodbye ends the session on arrival, and a
finishing peer must stay to deliver what its partner still needs. A goodbye that means "still
here" in one case would put a branch on the reason into every place one is handled.

**Two states after Running, and a condition each peer decides alone.** Finished when every
partner has finished at the same tick, this peer has run that tick, and the last hash check at
or before it has been compared with every partner. A finished poll reports `finished` and is not
an error. A finished session's goodbye is not sent.

**`PollReport::closed` stops being set, rather than being delivered.** The M18 plan listed it as
a bug to fix by delivering it. `Session::poll` set it in four places immediately before an error
return, so no caller ever saw it — and a session has nothing it means: under ADR-0017 a peer that
leaves ends the session, which is an error, and a run that is over is `finished`.

## What the tests found, three times

**One clause was another clause restated.** The record listed "every partner's turns up to the
last tick have arrived". The kernel runs a tick only once the gate has every turn for it, so a
peer that has run the last tick has had them all. The implementation writes the clause once, and
the record says why at the decision it changed.

**A clause test that could not fail.** Removing "this peer has run its last tick" survived the
case written for it, because that case finished at tick 24 — a check tick — and the hash-check
clause also waits for tick 24 to run. The case now finishes at 26, where only the clause under
test stands in the way.

**A claim in the record that was false for the case that mattered.** ADR-0020 said the
transport's silent-peer deadline covers a partner that never finishes. It does not cover one that
is connected and waiting — a peer told to run a longer game, stopped exactly one tick past its
partner's finish, which the session rightly allows, waiting for a turn nobody will send. The
mismatched-bounds case passed anyway, because at the default input delay the shorter peer
happened to announce one turn more and the session's own run-past check fired first. A mutation
removing the fix survived three runs out of three.

Only the application knows how long a run was meant to be, so the fix lives there:
`Session::declared_finish` reports the tick any peer has declared, and the lab compares it with
its own `--ticks` on every poll. The case now runs at an input delay of one, where the stall is
the usual timing, and requires the longer-running peer to name the disagreement. Unmutated it
passes in about a second; without the check it failed three runs out of three after the
transport's ten-second deadline, saying nothing about why.

**And one the lab needed that nobody predicted.** Both of its step loops ran every tick the gate
allowed, which is up to the input delay past `--ticks`. A peer that ran past the tick it finishes
at is refused by its partner, so both loops are now bounded. At the default delay removing the
socket bound also survived a run, for the same reason as above; the socket-agree case runs at a
delay of eight and catches it.

## Mutation checks

| Mutation | Caught by |
|---|---|
| Finished without the partner's finish | The partner-has-not-finished case |
| Finished before running the last tick | The run-the-last-tick case — **after moving it off the check interval** |
| Finished without comparing the last check | The held-hash-check case |
| Running past a finish not checked at poll | The run-past case |
| A finish at another tick accepted | The different-ticks case |
| A finished session still says goodbye | The held-hash-check case: the partner reads a lost peer |
| Finish past what was announced | The refusals case |
| The socket peer does not finish | The socket-agree case |
| The socket peer's steps unbounded | The socket-agree case — **after raising its input delay to eight** |
| The loopback's steps unbounded | The loopback-agree case |
| The loopback peers do not finish | The loopback-agree case |
| The lab does not compare a declared finish with its bound | The mismatched-bounds case — **after lowering its input delay to one** |

Three mutation runs did not compile on the first attempt and were rerun with compiling
variants; none is counted from its first attempt.

## Verification

- 1,007 tests passed in the debug preset, including 56 integration cases; the mismatched-bounds
  case five runs in a row before its input delay changed and three after.
- Format clean; clang-tidy 23 — the version the Linux lint job runs — clean, with each
  `vector<optional<Tick>>` element bound to a reference before it is tested, which that version
  requires to see the check and the use as one.
- Module boundaries and SPDX clean. All three goldens unchanged: nothing here touches the
  simulation.

## What is not proved

**A crash at the very end.** A partner that sends `Finish` and dies before this peer has compared
its last hash check leaves the run failed rather than completed. That is conservative on purpose
and recorded in `DEFERRED.md` with the condition for revisiting it.

**Chess finishing over a socket.** The session can finish; nothing has finished a game yet. That
is M22, where a result set at the same tick on every peer is the application's bound.
