# M27 — An installable engine, and chess in its own repository

Eleven commits on `m27-install`: the record at its gate, six slices, the prediction committed
before its measurement, three fixes found on the way, and the documents. Two in a new public
repository, [happyc0der/atlas-chess](https://github.com/happyc0der/atlas-chess). Decided by
[ADR-0024](../adr/0024-install-and-export.md), now Accepted with dated notes.

## What this milestone was for

The charter declares v1.0 when *"a game project links the engine, loads data, and runs a
deterministic simulation without patching engine internals"*. ADR-0018 D2 recorded that chess in
`apps/chess` could not prove that, because a game inside the tree can see everything, and D6
deferred moving it out until the engine had an install and export target. Nothing installed or
exported anything. On 2026-09-26 the owner asked for the next milestone and chose this one, and
at the plan chose: a new public repository started fresh; an SDK of two prefixes rather than a
second vcpkg setup; `apps/common` as an installed component; a proof on both sides; version
0.27.0; and an engine-owned fixture mod. Mid-milestone they decided a third thing: a consumer
compiles without floating-point contraction by rule, not by a flag the package imposes.

## What was built

**The package.** `cmake --install` writes every public header, by directory; every engine module
as the static library it is, exported as `atlas::<module>`; the app kit as the `app` component;
`AtlasConfig.cmake` with a `SameMinorVersion` version file; and `share/atlas` with the sprite
shaders, the engine's string table and the mod script. No internal header and no source file. A
profile or sanitizer build refuses to install, and says why.

- **Internal stays internal.** `atlas_add_module` gained `INTERNAL_DEPS`, which links an
  `*_internal` target only inside this build. Naming one under `DEPENDS` stops the configure.
- **The config refuses a consumer that could not link**, with the reason: a different compiler or
  major version, a lower macOS deployment target, on MSVC a build type of the other kind, and
  dependencies from more than one tree. MSVC's `/std:c++latest` travels as an INTERFACE option of
  `atlas::core`.
- **`tools/sdk.py <preset>`** installs, and prints `ATLAS_PREFIX`, `ATLAS_DEPS` and the rules.

**The proof here.** `tests/package/` is a separate CMake project that knows Atlas only as a
package. It runs the engine's golden scenario from its own tables and matches the installed
constants, brings up a script runtime, sends a message over a loopback link, resolves a key from
the installed `en.json`, calls the app kit, and compiles every installed header on its own under
its own warnings. A guard fails it if any include path lies in this source tree. Seven more
cases each break one thing and must fail at a named stage, printing a named message. Ten tests,
label `package`, on every lane.

**Chess, portable, then gone.** While still here, chess learned to read the engine's data from
where the engine keeps it (`--engine-data-dir`), gained its own texture generator, and had its
mod listed in a file rather than in the script. `tools/build_mods.py` became generic: a JSON mod
list, a guest include directory holding `atlas_mod.h` and nothing else, and a copy installed in
`share/atlas/tools`. The engine gained its own compiled mod, `painter.wasm`, which the lab runs.
Then atlas-chess was assembled, published on the owner's word and made green, and only then was
chess removed here.

## Predictions

Written into ADR-0024 before anything was built. **Four held, one missed, and four could not
fail as written**, because the work they forecast was done before the moment they described.

| # | Prediction | Outcome |
|---|---|---|
| 1 | The first `install(EXPORT)` fails on `platform_internal`, `atlas::sdl3` and the app libraries' include paths, and nothing else | **Could not fail.** Slice 1 fixed all three before any export was tried. Reverting the app-library fix alone stops the configure, checked once. |
| 2 | Chess's first configure fails only on build machinery, a test include and the harness; no engine header is missing | **Held** in the part that could still fail: the machinery was replaced first, and the first configure and build against the install had no error and no warning. |
| 3 | Chess's first run fails `--text-check` and the window cases on its data paths | **Could not fail.** Slice 4 gave chess `--engine-data-dir` first. The first run failed one case of 92, which nobody predicted: the opponent's manifest recorded repository paths. |
| 4 | On MSVC, without the exported flag, a consumer compiles under another `/std` and links | **Could not fail.** The flag was exported in slice 1. The package test's guard confirms every consumer compile uses Atlas's flag on Windows. |
| 5 | On Windows, executables fail at start-up until the DLLs are copied | **Could not fail.** The copy was written first; the consumer and chess ran on Windows. |
| 6 | The golden hashes are unchanged in both repositories | **Held.** The engine's from a consumer on six lanes; the Opera Game's in atlas-chess on four. |
| 7 | The fixture changes one benchmark row and nothing else | **Held.** But the number predicted for that row, committed separately, missed; see below. |
| 8 | No public header needs `_CRT_SECURE_NO_WARNINGS` | **Held.** Every installed header compiled alone under `/W4 /WX` on MSVC Debug and Release. |
| 9 | A chess CI run whose cache misses takes about forty minutes | **Missed**, pessimistically. Every lane was cold, with no cache at all, and took 5 to 10½ minutes. |

Four predictions that could not fail is a lesson about when to write them: at the gate, before
the plan that pre-empted them was final. The ones that could fail were those about things nobody
controlled — compilers, headers, hashes and time.

## Found on the way

None of these was predicted, and each was fixed or recorded.

- **`atlas/simulation/golden.hpp` could not be included on its own.** It used `std::size_t`
  without `<cstddef>`; every file in the tree that included it had included that first. The
  package test's header check found it on its first honest run. The only one.
- **The package test's warnings were decorative at first.** An imported target's include
  directories are system directories, in which no warning is ever reported, so `-Werror` in a
  consumer could not have caught anything in an Atlas header. The consumer sets
  `NO_SYSTEM_FROM_IMPORTED`; every header still compiles clean.
- **`rhi` had given the window handle's include path to twelve directories.** `DEPENDS` links
  PUBLIC, so everything above `rhi` compiled with the internal header in reach: renderer, scene,
  edit, animation, tools, the three applications and the benchmarks. Now two.
- **SDL3 resolved to Homebrew's copy** when the vcpkg tree was missing from a consumer's path, and
  only the next package's absence stopped the configure. The config now requires every
  dependency from one tree.
- **A consumer must switch off CMake's C++20 module scan.** Under Ninja with clang it needs
  `clang-scan-deps`, which the Linux container lacks; AppleClang is never scanned, so macOS could
  not have shown it. A package cannot carry Atlas's own setting, so it is a rule of the contract.
- **`build_mods.py` crashed at a shallow path.** It computed `parents[2]` of `/src/tools` before
  looking anywhere; the Linux container, whose checkout is `/src`, found it.
- **The formatter had never checked C.** It looked for `.cpp`, `.hpp`, `.h` and `.inl`, so the
  mods' freestanding C went unchecked from M26, and the painter from the day it was written. Now
  it checks `.c` and `assets/source/mods`; formatting left both modules byte for byte the same.
- **Floating-point flags are not carried by the package.** Found while writing atlas-chess's
  build; decided by the owner as a rule of the contract (ADR-0024 D9).

**Corrected in the record.** The slice 3 commit message counted eight cases that break one thing;
there were seven. The M15-era `DEFERRED.md` entry and M26's reading of `script/load` both took the
benchmark's empty "trivial" module for the 295-byte `synthetic.wasm`; both are corrected where
they were written.

## Benchmark impact

`script/load`'s compiled-module row loads the 457-byte painter instead of the 8 KB opponent. The
prediction, committed before any run, was 5.3–8 µs and at most 1.5 times the trivial row; the
result was **9.1–10.6 µs, 1.77–1.94 times**. Not the declared memory: a one-page painter loads
the same. The trivial row is an empty module with no imports or data, and `synthetic.wasm`,
which has both, loads in 8.7 µs; the painter's own bytes cost what was assumed.
`docs/PERFORMANCE.md` has it all. `atlas_bench` no longer has a `chess` group.

## The charter's test

**As written, it is met.** atlas-chess links the engine through `find_package` against an
install; loads data — its own string table, textures and mod, and the engine's shaders and table
from `share/atlas`; runs a deterministic simulation whose golden hashes agree on macOS, Linux and
Windows; and patches no engine internal, as its compile commands show and its build rules
forbid. Two things are fair to weigh against it. It is one game, written by the hands that wrote
the engine. And the engine was changed for it in M19 and M21, properly and by record, before it
left. **Declaring v1.0 is the owner's**, and it would commit the installed API to semantic
versioning, which `SameMinorVersion` at 0.x deliberately does not.

## Remaining risks

- **A change here is seen in atlas-chess only when it moves its pin.** A hashing change fails
  chess's golden test there, later. Recorded, with a scheduled cross-repository build as the
  remedy if it bites.
- **atlas-chess's binaries find the engine's data by an absolute path** baked in at configure.
- **Windows is covered by chess in Debug only**, and neither repository sanitizes chess.
- **The SDK cache in atlas-chess is keyed on the pin**, so every pin move rebuilds every
  dependency: five to ten minutes a lane, measured.
