# M26 — Chess: a mod as the opponent

Nine commits on `m26-mod-opponent`: the record at its gate, two fixes to the mod host, four
slices, the prediction committed before the measurement, and the documents. Decided by
[ADR-0023](../adr/0023-mod-authoring.md), now Accepted with dated changes.

## What this milestone was for

ADR-0018 D7 made a mod opponent its own milestone, and the owner deferred it because it forces a
decision larger than chess: **nothing non-trivial could be authored for the sandbox.** Every mod
was written byte by byte by `tools/gen_mods.py`, which has no loops, branches or locals. On
2026-09-25 the owner asked for the plan and chose: C compiled by clang; a mod carrying its own
rules and a two-ply search; local play only; Homebrew's `lld` for the linker here.

## What was built

**A toolchain for mods.** `tools/build_mods.py` compiles freestanding C to wasm32 with clang and
links it with wasm-ld of LLVM 23, with the target features pinned and every name stripped, and
commits the module with a manifest of the toolchain and a hash of every input. Its check has four
parts:
- the inputs against the manifest, on any machine;
- the committed module against the hash the manifest records, on any machine;
- a rebuild's bytes, only on the manifest's own toolchain;
- and, where a toolchain and the chess application both exist, the rebuilt module and the
  committed one playing the same game against themselves.

The lint job and the Linux build lanes install the toolchain, and CTest hands the check the
lane's own chess binary.

**The opponent.** `apps/chess/mod`: rules in C that use the board table's own encoding, and a
two-ply search on material that sees a mate it gives, a stalemate and a mate it would walk into.
It evaluates two of its moves a tick, keeping its state in linear memory, breaks ties with the
host's seeded generator, and never submits twice for one position. 8,108 bytes.

**The chess application plays it.** `--mod chess_opponent.wasm` with `--mod-plays white`,
`black` or `both`; with `--moves` the list is the person's, played in turn. The position reaches
the mod as bytes laid out by one C header both sides include. `chess.players` names the mod's
identifier, so the rules decline it out of turn as they decline a person, and now accept it when
a save loads. The lab's mod loading moved to `atlas::app_mods`, chess being its second user.

```
atlas_chess --headless --mod chess_opponent.wasm --moves e2e4,d1h5,f1c4,h5f7
ply 8: e8f7 (the mod)
opponent: mod 'chess_opponent.wasm' plays black, 4 move(s) submitted, still running
```

## What changed from the record

Each is a dated note in ADR-0023.

- **The quota is two moves a tick, not four.** Measured at four, the worst tick was 2.16 M
  instructions, 4.6 times under the budget — on seven positions. One move facing the most replies
  any position allows would have left a margin of two and a half.
- **The check has four parts, and the fourth needed a binary.** No CI job had both a toolchain and
  a chess build, so the Linux build lanes now install LLVM 23.
- **The application check for a saved mod has no call site**, because the chess application does
  not save. The table rule and the round trip are proved in a test.
- **The features are named** — bulk memory, sign extension, mutable globals over `mvp` — and the
  view layout is one header.

## Found on the way

**Two defects in the mod host, from M15, found by the first compiled module.**

- **The debug clock could leak into a safe runtime.** WAMR sorts the import array it is given in
  place, and the host handed it one shared array whose first nine entries were the safe set. A
  runtime created with the clock sorted all ten, and the next runtime in the same process then
  offered the clock and lost `atlas_view_size`. No program creates two runtimes; the tests do, in
  random order, and failed one run in three. A regression case fails five runs in five on the old
  code.
- **Every load of a compiled module drew a warning.** WAMR reshapes the memory of a module that
  never grows it, and the host's override then exceeded the reshaped maximum. The host now leaves
  the maximum to the module, which its own check had already bounded.

**Recorded, not fixed:** a command type is a hash returned as a signed integer, so one that hashed
to −3 would read as `ATLAS_ERR_REFUSED`. The opponent tests for zero only.

**Twice in this milestone a test passed by luck and was caught.** A self-chosen stress position
had one side already mated, so its search "failed" for a reason unrelated to the budget; and the
first mutation run of the opponent had two survivors that became the mate and seed tests.

## Checks

| Where | Added |
|---|---|
| Rules, natively | perft on six positions and every shallower depth; a comparison with `chess_sim` over 300 random games, 20,000 positions and 500,000 moves, byte for byte |
| The opponent, in the runtime | a legal opening, a free queen, mate in one, a mate it must not walk into, its turn, one submission, different seeds, self-play twice, a save resumed, every stress position within a quarter of the budget, and a hidden measurement |
| The view | every offset, clocks past a byte, the outcome |
| The script host | the clock cannot leak across runtimes |
| Integration | self-play to a result twice to one hash; a person's Scholar's mate attempt; the option refusals; the mod in a window |

Twenty-three mutations, each caught:

| Slice | Mutations |
|---|---|
| The toolchain's check | a stale source, a module replaced by hand, changed flags, a different toolchain skipped loudly, same toolchain with different bytes, no toolchain skipped loudly |
| The rules | no en passant, castling through check, a promotion piece forgotten, an en passant file with no capturer, the halfmove clock kept by a capture, a captured rook keeping its right |
| The opponent | a mate it gives unseen, submitting every tick, ignoring its seat, a mate it walks into unseen, no tie-break draw, the quota ignored, the side read from the wrong byte |
| The application | the mod given no seat, applied moves not recorded, the views in the wrong order, a mod refused as a player |

Three of the rules mutations are caught only by the comparison with `chess_sim`, because perft
counts cannot see them. And a committed module built differently but matching its manifest passes
the byte-skipping check and fails the behavioural one, which is what that part exists for.

## Benchmark impact

Predicted before any run, in `docs/PERFORMANCE.md`, and both held.

| Measurement | Result | Predicted |
|---|---|---|
| Worst tick, quota four | 2.16 M instructions | 0.5–2.5 M |
| Start position tick, quota four | 0.43 M | about 0.3 M |
| Worst tick, quota two | 1.16 M | — |
| Loading the opponent | 38.2 µs | 20–80 µs |
| Loading the trivial module, same runs | 5.1 µs | — |

The machine was not idle during the load measurement, so the two loads are paired within each
run. Instruction counts are the runtime's own meter and do not depend on the machine.

## Remaining risks

- **Windows and Linux have not built any of this.** The C rules compile as C with MSVC for the
  first time in CI, and the Linux lanes install LLVM 23 for the first time.
- **A save taken mid-search does not resume exactly.** Recorded, with its trigger.
- **The opponent is weak by design.** Two plies, no knowledge of repetition or the fifty-move rule.
