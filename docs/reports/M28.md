# M28 — A real GPU on Windows: Vulkan on an RTX 3080 Ti

Six commits on `m28-windows-vulkan`: the record at its gate, the fix, the runner, the benchmark
prediction before its run, the measurements, and the documents. Slice 1, which installed the tools
and reproduced the failure, changed nothing in the tree. Decided by
[ADR-0025](../adr/0025-windows-vulkan.md), now Accepted with dated notes.

## What this milestone was for

The roadmap's largest risk was that *"no real non-Apple hardware has ever run this code"*, and
beside it, *"no local Windows machine"*. Hosted Windows runners compile and test every push but
have no GPU, so the `gpu` label had never run on Windows. The owner's laptop, `msi` — an NVIDIA
RTX 3080 Ti Laptop GPU and an i9-12900HX, reachable over SSH — removed the excuse. On 2026-09-26
the owner chose this milestone and decided: Vulkan now and Direct3D 12 as its own milestone; the
correct tools installed on the laptop; a script over SSH rather than a self-hosted runner, because
the repository is public; and the logged-in desktop session usable for what needs a window. On
2026-09-27 they changed one of those: Visual Studio 2019 stays, because CUDA 12.1 accepts no newer
host compiler.

## What was built

**Windows renders on Vulkan.** Two changes, both small:

- **SDL is built with Vulkan on Windows.** `vcpkg.json`'s `vulkan` feature covered Linux only, so
  Windows' SDL had one GPU backend, Direct3D 12. SDL's own configure log said so:
  `GPU drivers: d3d12`.
- **The device asks only for the shader formats Atlas ships.** It asked for SPIR-V, MSL and DXIL;
  Atlas has never shipped DXIL. SDL takes the first backend in its order that accepts a format
  asked for, and Direct3D 12 comes before Vulkan. Now one list, `rhi::kShippedShaderFormats`,
  names SPIR-V and MSL; the device requests exactly those and the loader walks the same list.

**A test that catches the class of mistake without a GPU.** `rhi_backends`, label `unit`, asks SDL
which backends the build contains and requires one that takes a shipped format, that the device
asks only for shipped formats, and that every compiled backend has a name Atlas knows. On the
laptop's old SDL it failed naming the cause:

```
the library was built with: direct3d12
```

**Two fixes the laptop found, which no Mac could.**

- **`Window::display_scale()` broke its own contract on Windows.** It promises pixels per logical
  unit, and returned SDL's display scale, which also carries the user's interface scaling: on a
  Retina display the two are equal, and on this laptop, at 175%, it returned 1.75 for a window
  whose pixels equal its logical units. A click in the lab picked a cell 1.75 times too far from
  the pointer. It now returns the pixel density. A new GPU case fails under the old code on the
  laptop — `logical 256x256, pixels 256x256, display scale 1.75` — and passes on the Mac and on
  llvmpipe either way.
- **The lab's live pick check compared a pixel's centre with its corner.** The identifier pass
  reads the pixel's centre; the analytic inverse was evaluated at its corner. It now uses the
  centre, as the GPU test of the same pass always did.

**The run, as one command.** `tools/ci/windows_gpu.sh` checks a pushed commit out on the laptop,
runs `tools/ci/windows_gpu.ps1` there, and copies the logs and screenshots back, as PNG, to
`build/windows-gpu/<commit>-<preset>/`. The PowerShell script builds from SSH's session 0 and runs
the `gpu` label, a sandbox and a lab screenshot, and with `--bench N` the GPU benchmark groups, in
the owner's desktop session, through a scheduled task that is run once, waited on and deleted. It
fails, by name, on a failed or **skipped** test, a device on any backend but Vulkan, a validation
error, a missing screenshot, or a benchmark group with no results.

```
$ tools/ci/windows_gpu.sh 8eb3b35
desktop session: ran for MSI\KESHAV, task result 0
gpu tests: 63 run, 0 failed, 0 skipped
backends seen: vulkan
validation errors: 0
windows gpu: passed on 8eb3b35329c9
```

Two presets, `windows-msvc-debug-gpu` and `windows-msvc-release-gpu`, mirror `macos-debug-gpu` and
ask the Vulkan loader to leave implicit layers out, which it does for most of them.

## Predictions

Written into ADR-0025 at the gate. **Three held and five missed.**

| # | Prediction | Outcome |
|---|---|---|
| 1 | Unchanged, the laptop passes CI's set and every shader-loading `gpu` test fails | **Held.** 1013 of 1013; in the desktop session the device came up as `direct3d12`, accepting DXIL alone, and 15 tests failed: every quad batch case, the cell field, the identifier pass and the pick. The overlay's passed, because Dear ImGui's SDL backend carries its own shaders in every format. |
| 2 | The backend test fails on Windows before the fix and passes after | **Held**, naming the cause. |
| 3 | After the fix, with no renderer change, every `gpu` test passes | **Missed.** The renderer needed no change; the platform and the lab did. |
| 4 | Zero pick disagreements | **Missed**, once: 3062 against 3061, which was the display-scale bug seen end to end. None since. |
| 5 | From session 0 a device works and a swapchain does not | **Missed.** That was true of Direct3D 12. On Vulkan session 0 presents and all 63 tests pass there. |
| 6 | Validation reports at least one warning in Atlas's use of SDL_GPU | **Missed.** The layer loaded (the loader's own debug output shows it inserted) and its messages reached the log, and across 63 tests it reported nothing; best-practices checking on one test, nothing either. |
| 7 | The GPU benchmarks land within ±50% of the M4 Pro | **Missed** on every timed row, by 2.6 to 15 times; see below. |
| 8 | Rebuilding SDL with Vulkan adds under five minutes to a cold Windows CI build | **Held.** 57 s in Release, 1.2 min in Debug. |

The pattern is the useful part. The predictions about the renderer were too pessimistic: it needed
nothing and validation found nothing. The ones about everything around it were too optimistic,
and each miss was a finding.

## Found on the way

- **From SSH, the unfixed GPU tests skipped, and CTest called it a pass.** Session 0 could not
  create a Direct3D 12 swapchain, Atlas creates its device with the window's swapchain, so 55
  cases reported "no graphics device" and the summary read `98% tests passed` for a machine that
  had drawn nothing. The runner reads CTest's JUnit report, where a skip is a skip.
- **Session 0 has no display scaling**, so the display-scale case passes there under the broken
  code. That, not presenting, is why the runner uses the desktop session.
- **The runner once passed the wrong commit.** An untracked copy of the script on the laptop
  blocked `git checkout`; the three git steps were joined by semicolons, so the failure was
  ignored and a run asked for `1585351` built, tested and passed `8eb3b35`. The engine was the
  same in both, so no result was wrong, by luck. Each step now stops the run and HEAD is checked
  against the commit; against the same blocked checkout it exits 2.
- **A device test counted DXIL as a format Atlas could produce**, so a device able to draw nothing
  of Atlas's passed it. It counts the shipped list now.
- **Benchmarks are off by default in a build**, which CI switches on and the runner at first did
  not; the first benchmark run found no executable and failed, as it should.
- **Two implicit layers load anyway.** `VK_LOADER_LAYERS_DISABLE=~implicit~` did not stop an
  overlay's layer and NVIDIA's presentation layer. Neither said anything. Recorded.
- **M27's report claimed a local clang-tidy run that never happened.** `precheck.sh` runs tidy only
  with `ATLAS_PRECHECK_TIDY=1`. Corrected in `reports/M27.md` with the date; CI's Lint had run it,
  green, and M28's own local run with tidy switched on was clean.

## Benchmark impact

None on any existing row: no engine code in a timed path changed. The new numbers are the laptop's,
recorded in `docs/PERFORMANCE.md` against a prediction committed first, and that prediction missed.
Best medians of nine runs, against the M4 Pro's best of nine measured the same day:

| Scenario | Laptop | M4 Pro |
|---|---|---|
| quads 100k | 9,745 µs | 648.5 µs |
| quads 10k | 246.6 µs | 92.4 µs |
| cells 1,048,576 | 2,373 µs | 273.2 µs |
| cells 102,400 | 131.0 µs | 50.2 µs |
| cells 10k | 84.2 µs | 31.0 µs |
| allocations per frame | 2 | 8 |

A probe on the laptop, never committed, put the time in building the instances, at 50 to 80 ns a
quad at 100k against 13 at 10k and before any upload, and in the copy into SDL's mapped memory,
which fell from 16 GB/s to 2 GB/s as it grew. A plain loop doing the same reads and writes with no
engine and no GPU took **33 ns a record on the laptop and 1.16 on the M4 Pro**. The large rows
measure the laptop's memory; why it streams at 3.9 GB/s — both modules reported on one channel at
3600 MT/s, the Balanced power plan — was not separated, and changing either is the owner's. The
small rows are 2.7 times the Mac's, and pinning to the efficiency cores alone made 10k quads 3.5
times slower.

## Remaining risks

- **The Windows GPU run is outside CI.** A renderer change is verified on Windows when somebody
  runs the script, which CLAUDE.md now requires for changes to `rhi`, `renderer`, the lab's view
  and the platform's window. The laptop must be awake, on the network, and logged in and unlocked.
- **One GPU, one vendor, one of SDL's two Windows backends.** Direct3D 12, AMD, Intel and arm64
  Windows are open, each with a trigger in `DEFERRED.md`.
- **The overlay is small on a scaled Windows desktop.** Correct placement, unscaled fonts; recorded.
- **The laptop's benchmark numbers stand for the laptop.** Until the machine's memory is
  understood, they say nothing about Windows or about MSVC.
