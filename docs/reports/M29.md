# M29 — The machine, measured

Six commits on `m29-machine-benchmark`: the record with its predictions, the group, two fixes
that only MSVC could find, the documents, and the M4 Pro's machine rows recorded as its baseline. No ADR: this is tooling, installed nowhere and
reaching no consumer, and it is recorded in `docs/PERFORMANCE.md` as M23's was in its report.

## What this milestone was for

M28 measured the engine on the owner's Windows laptop and found it 2.6 to 15 times slower than on
the M4 Pro. It took a loop written by hand, with no engine in it, to show why: the laptop streams
memory thirty times slower. Until then a slow machine read as a slow engine, and nothing in
`atlas_bench` could have said otherwise. On 2026-09-28 the owner asked for everything that did not
need the laptop; this was the first of the two candidates that qualified.

## What was built

**A `machine` group** in `atlas_bench`, which needs no graphics device:

- `machine/stream` reads a 64-byte record and writes one, at 32 KiB, 1 MiB, 8 MiB and 64 MiB of
  reads and writes together: how fast memory moves at each size.
- `machine/chase` follows a random cycle of pointers through 64-byte nodes, one dependent load at
  a time, at 32 KiB, 1 MiB and 64 MiB: how long one miss takes where the working set lives.
- `machine/chain` is a dependent 64-bit multiply and add: how fast one core is, with nothing to
  overlap.

Each iteration does about a million units, and each row **checks its own answer and aborts if it
is wrong**: every record against its source and the last pass's stamp; the cycle for visiting
every node once and ending where its visiting order says; the chain against its closed form,
computed by squaring. A machine benchmark the compiler had deleted would report a superb machine.

**Every result names its machine.** Linux reads the processor, board and memory from `/proc` and
`/sys`, with an arm64 fallback that names the implementer and part; Windows reads the registry;
macOS already used `sysctl` and now records memory too. JSON strings are escaped, since a
machine's name now comes from the system. The laptop's M28 results said `unknown`.

**The baseline tool reads the machine rows.** `compare` marks a machine row that moved as
`MACHINE`, never a regression, and says before the regressions that they may be the machine's.
`across a.json b.json` sets two files side by side, machine rows first, with nanoseconds per unit,
and fails nothing, because a ratio between machines is not a regression.

**It runs everywhere.** CI's benchmark self-check runs the group in all six lanes, so every log
now names its runner, and `windows_gpu.ps1` runs it first among its groups.

```
$ atlas_bench --filter machine
machine   : Mac16,7 (Apple M4 Pro, 14 hardware threads, 24 GB)
machine/stream                     64 MiB                    1.412ms ...  742.53M records/s
machine/chase                      64 MiB                   98.099ms ...   10.69M loads/s
machine/chain                      4M steps                  3.740ms ... 1121.57M steps/s
```

## Predictions

Written into `PERFORMANCE.md` in `fe909e8`, before any of the code existed.

| Prediction | Outcome |
|---|---|
| Eight M4 Pro rows, each in a stated range | **Seven held.** Chase at 1 MiB measured 6.07 ns against at most 6: second-level latency is about 27 cycles here, not eighteen. |
| The M4 Pro's spread under 1.3× | **Held**, at most 1.05×. |
| GitHub's Linux x86_64 runner: chain, chase 64 MiB and stream 64 MiB in stated ranges | **Held**, all three: 1.25 ns, 113 ns, 4.44 ns on an EPYC 7763. |
| The Windows runner within 1.5× of the Linux one on every row | **Held**: 0.85× to 1.27× on all eight rows, on the same EPYC 7763. MSVC and Windows cost nothing on the chain and the chase and up to a quarter on the stream. |
| The laptop: stream 64 MiB at least ten times the M4 Pro's, chain within 1.5× | **Not yet scored.** It waits for the laptop's next `windows_gpu.sh --bench`; the owner asked for work that did not need the laptop. |

**The code changed after its first run, and that is said here rather than hidden.** The stream
first copied field by field, compiled to sixteen scalar stores a record, and read 2.2 to 2.5 ns at
every size from 32 KiB to 64 MiB: eight cycles of stores, the benchmark's own instructions. The
chase first followed indices and paid an address calculation before each load. Both now do what
the record describes — whole records, "eight vector moves"; pointers, "one dependent load at a
time" — and the predictions were not touched. A row that reads the same in the first-level cache
and in memory is not measuring memory, and that is the one thing this group must not get wrong.

## Found on the way

- **Lanes of one CI run land on different processors**: an EPYC 7763 and an EPYC 9V74 under
  Linux, an EPYC 7763 and a Xeon Platinum 8573C under Windows. Nobody could have read that from a
  log before; now the first line of the benchmark step says it.
- **One M4 Pro core streams at about 95 GB/s from 1 MiB to 64 MiB alike.** Past the first-level
  cache the limit is the core, not where the bytes are.
- **Two errors only MSVC could find**, each a Windows-only build failure found by CI: defining
  `WIN32_LEAN_AND_MEAN` and `NOMINMAX`, which the build's common options already define, and
  C4324 on the node's implicit padding. The laptop could have found both before pushing; this work
  was to need no laptop, and CI found them instead, which is what it is for.
- **README's milestone count had not moved since M27.** M28's documents missed it; fixed here.

## Mutations

| What was broken | What caught it |
|---|---|
| The stream skips its last record | "record 255 field 0 was not copied" |
| The stream's last pass writes no stamp | "record 0 was not written by the last pass" |
| The cycle built by Fisher and Yates instead of Sattolo, so not one cycle | "node 0 visited twice; not one cycle" |
| The chain skips one step an iteration | "the end of the chain differs from its closed form" |
| A slower machine, against a doctored baseline | `compare`: the machine rows marked `MACHINE`, the engine row still `SLOWER`, with the note |

## Benchmark impact

No engine row changed: nothing under `engine/` was touched. The group's own numbers are in
`PERFORMANCE.md`, and the M4 Pro's are recorded in this machine's baseline, so `compare` can now
say when the machine is what moved.

## Remaining risks

- **The laptop has not run the group.** M28's explanation of the laptop is still a hand-written
  loop's until it does.
- **The machine rows are single-core.** A parallel row, and how a hybrid processor schedules it,
  are not measured; `DEFERRED.md`'s entry on pinning to one kind of core still stands.
- **`across` prints ratios, not reasons.** Which machine row explains which engine row is the
  reader's judgement, and the tool does not pretend otherwise.
