# M19 — A command may be declined

Seven commits on `m19-declined-commands`. Decided by
[ADR-0019](../adr/0019-declined-commands.md), the first of the two engine changes
[ADR-0018](../adr/0018-chess-probe.md) said chess would force and that the lab already needed.

## What this milestone was for

A command had two fates the kernel could name — late and invalid — and a third it could not: a
well-formed command, delivered on time, that the world refuses. `apply` returned `void`, so
every handler in the tree that met the third fate returned early and said nothing, and the
kernel counted the command as applied, recorded it as applied, and hashed on.

That was not an abstract complaint. The lab's `set_color_index` had a comment explaining it
was refusing on state and a `return;` doing it. The synthetic scenario every lockstep proof
runs on did the same twice. And M14's proof that two peers refuse identically had to **write
the refusal into the world** to make it observable at all, with a comment saying a silent
no-op would be indistinguishable from the command never arriving. That comment was the
finding. Chess would need the third fate sixty times a game; the engine needed it already.

## The design, in one paragraph

`apply` receives an `ApplyContext` — who submitted the command and at which tick — and returns
a `Status`. An error is a **decline**. It is deterministic by construction, because it depends
only on world state and the payload, which every peer holds identically at that tick; so it is
counted on its own, in `TickReport::commands_declined`, apart from `commands_invalid` (bad
bytes) and from `commands_applied` (changed the state). It is logged at debug, not warning,
because a game would otherwise warn on every illegal attempt. It is not recorded, because a
recording is of what changed the state. And the contract is that **a handler that declines has
changed nothing** — which the kernel cannot check, so every test of a declining handler hashes
the world against a twin that was sent nothing.

## The migration, and its exit criterion

Twelve `apply` lambdas, not the eleven the plan counted, took the new signature and returned
`ok()` in one commit in which nothing declined. The exit criterion for that commit was silence:
every golden hash byte-identical and every existing test passing unchanged. Both held, which
is the strongest evidence available that changing the signature of every command handler in
the tree changed nothing the simulation could see.

## Three real declines, and what the first one found

**The lab.** The plan said its early return on the cell bound was the hidden refusal. It was
not reachable: the queue re-runs `validate` against the same bound an instant before `apply`,
so on one thread the decode cannot fail there. What the handler never checked was **the table
it was about to index**. The bound is the application's claim about the grid and the table is
the world's; they agree in every run the lab makes, and nothing enforced it. A bound that
lagged a load would have passed validation and written past the end of the table. The handler
now declines a cell the world does not hold, the test provokes it by inflating the bound, and
ADR-0019 D7 carries a dated correction rather than an edit.

**The synthetic scenario.** A row out of range declines with its reason; a missing table is an
assertion, because a fixture registered against a table the world lacks is a mistake and not a
state. Two kernel cases: a decline is its own fate, and two kernels fed the same commands make
the same declines at the same ticks.

**The net harness.** `kClaimIfFree` claims a cell or is declined because somebody owns it,
with no side effect on the refusal. The lockstep case M14 could not write: both peers claim the
same cell every tick, the total order decides whose claim is applied and whose declined, most
of the run is declines once every cell is owned, and the two peers agree on the count and the
hash at every tick with the recording fixture's contest counters at zero. A second case checks
the contract directly against a twin.

The lab's statistics row and its final log line gain a `declined` count. The integration
regexes match the line's prefix and did not move.

## Mutation checks

| Mutation | Caught by |
|---|---|
| The kernel counts a decline as invalid | `commands_rejected() == 0` and the split counts, in the kernel case and the lab case |
| The kernel records a declined command | `applied_commands.empty()` |
| The lab writes the cell unchecked | The lab case: declined 0, applied 1, hash differs from the twin |
| The claim writes the owner before declining | The twin case: hashes differ |
| The bump writes row 0 before declining | The kernel case: hash differs from the twin |

One survival of a different kind: the "two kernels decline alike" case failed on first run,
and the kernel was right. The test let its in-range row run from sixteen to nineteen on a
sixteen-row table and got three declines it had not asked for. The test now wraps, and says so.
The mutation run also had to be repeated once because Catch2 splits a test name on commas, so
the first run of the lab mutation ran no test at all and reported exit code 2; it is recorded
here because a mutation check that ran nothing looks, in a log, very like one that passed.

## What is not proved

**That a handler in a game will honour the contract.** "A handler that declines has changed
nothing" is tested for the three handlers here and is a rule for the ones chess writes. The
kernel cannot enforce it; a debug-build option hashing around every command is recorded in
`DEFERRED.md` with the condition that would justify it.

**Anything on the wire.** A decline is not sent, by design; every peer makes its own. Nothing
in `net`'s protocol changed and `kProtocolVersion` is still 1.
