# M25 — Dropping a peer

Six commits on `m25-peer-drop`: the record at its gate, the relay, the drop, the lab, the
benchmark's prediction, and the measurement with the documents. Decided by
[ADR-0022](../adr/0022-dropping-a-peer.md), now Accepted with dated changes.

## What this milestone was for

The last of the three items M17 left open, in the order the owner chose on 2026-09-24. The
deferral's trigger was a consumer for whom one person's connection ending everyone's session is
worse than the risk of getting the agreement wrong. **That trigger had not fired, and ADR-0022
says so first.** The lab is the consumer, as it was for M17 and M24.

## What the survey found first

**A socket session could not have more than two peers**, although the lab accepted `--expect 16`
from M17 on. The socket hub is a star: a connector held a connection to the listener and nobody
else, and the session broadcasts. Three processes all exited 1 before the first tick, and no case
had ever started three. The in-memory mesh ran three peers correctly, which is how it went
unseen. The fix is a relay, and the relay also turned out to be the answer to the drop.

## What was built

**The relay.** A connector broadcasts once, to the listener, marked for everyone. The listener
files the message for itself and forwards it to every other connector in the same step, framed
with where it came from. So the listener holds everything it forwards, and each connector
receives the listener's messages and the forwarded ones in the one order the listener produced.
No index is announced until every connector has arrived, the index message carries the session's
size, the deadline is per peer, and a connector cannot address another connector directly.

**The drop.** Under `PeerLoss::Drop`, when the listener's transport loses a connector, the
listener's session reads everything that connector sent and announces `Drop{source, turns}`: how
many of its turns it received, which is how many it forwarded. Every other peer reads everything
forwarded from the lost peer, checks it holds the same count, and stops expecting it through
`TurnGate::expect_sources`. No acknowledgement round is needed. Ending the session stays the
default, on the hub and on the session.

**The lab.** `--drop-lost-peers` sets the policy on both, prints each drop, and reports how many
peers remain.

## What changed from the record

Each is a dated note in ADR-0022.

- **The agreement is on a count, not a tick.** The lost peer's own stream to the relay can have a
  gap, and then "the highest tick the relay holds" names a set nobody can reconstruct. Every peer
  holds the same set, because the relay forwarded exactly what it received, so every peer agrees
  on its size. The case with a gap is in the tests.
- **No goodbye reason was added.** The transport closes a lost connector's connection before the
  session knows, so a slow connector already ends with its own reason.
- **The hub takes the policy too**, because under `End` it ends before the session sees anything.
- **The relay gained two rules**: indices held back until everyone arrives, and a deadline per peer.

## Found on the way

**A session could read a turn before a third peer's announcement, and refuse it.** A session
reads each peer's inbox in turn, so the order between senders is lost. The first run of three
processes met it one run in forty under load, and every process exited 1. It predates the relay:
the in-memory mesh had the same window whenever one announcement was slower than another peer's
first turn. A session still handshaking now reads only announcements and leaves the rest queued.
A test holding one announcement back fails without the fix, and sixty runs under load then passed.

**Three mutations first failed to compile**, because removing a call left a parameter unused,
which is an error here. They were rerun as compiling variants. **Two survived their first
correct form**: the relay counting before reading everything, and a connector comparing before
reading. The lockstep cases never delivered a forwarded turn in the same poll as the drop, or
more than sixty-four messages at once. Each got a test built to produce exactly that order, and
both are caught now. **One mutation run was polluted by a bug in the test**: the three-process
case assumed which connector became peer 1, and the connectors race. Its results were discarded,
the case now reads each index from its own output, and the unit-level results stand.

## Benchmark impact

Predicted before any run, in `docs/PERFORMANCE.md`, and both held. The machine was not idle: a
browser used about two cores throughout, so every comparison is paired within a run.

| Scenario | Median | Predicted |
|---|---|---|
| Relayed round trip, joiner to joiner | 42.4 µs | 40–60 µs |
| Direct round trip, for comparison | 21.1 µs | — |
| Session poll, four peers, star | 10.7 µs | within a fifth of the mesh |
| Session poll, four peers, mesh | 12.0 µs | — |

The relay doubles the latency between two joiners and costs nothing measurable per tick.

## Remaining risks

- **Linux and Windows have not run any of this.** Every socket case was verified on this Mac. The
  relay changes the socket hub on all three platforms, and CI will be the first to show it.
- **The listener is trusted.** It can forge any connector's messages. With three peers that is a
  real widening, recorded rather than fixed.
- **The relay carries every message twice.** Measured here in one process; across a real network
  the second trip is a second crossing of the wire, whose cost depends on where the host sits.
- **A drop's meaning is left to the application.** The lab prints it; chess, with two players,
  still ends.
