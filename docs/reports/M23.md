# M23 — One pin for vcpkg

One commit on `m23-one-pin`. No ADR: nothing here is expensive to reverse.

## What this milestone was for

The owner asked to go back to the plan as it stood before chess and continue it. That plan
ended at M17, which called itself the stopping point and left three items recorded with triggers,
none of which has fired. The owner chose all three, in order, one milestone each: this one; a
string API for mods (M24); and dropping a peer without ending the session (M25).

## The gap

Every build workflow keys its vcpkg binary cache on a hash of `vcpkg.json`, `.gitmodules` and the
overlay ports. The pinned vcpkg commit is in none of them as such: `.gitmodules` holds a path and
a URL, and the commit lives in the submodule's gitlink and again in `vcpkg.json`'s
`builtin-baseline`. The key follows the baseline. Bump the submodule without the baseline and
every lane restores a cache built against a different port tree, with nothing to say so.

M17 found this and recorded two fixes: the cheap one, hashing the submodule's commit into the key
as well, and the honest one, stopping there being two pins. This milestone took the honest one,
with a caveat: neither record can be removed, because vcpkg resolves against the baseline and the
build checks out the gitlink. So the two are held to one value instead.

## The fix

`tools/check_vcpkg_pin.py` reads the gitlink from the index — so a bump that is staged and not
yet committed is judged too — the baseline from `vcpkg.json`, and the commit the vcpkg row of
`docs/DEPENDENCIES.md` names, which the survey found was a third record, and fails naming all
three when they disagree. It runs as a lint test, as a precheck step, and as a step in the lint
workflow, before any cache is consulted. With it in place the existing key is sufficient, because
the file it hashes cannot name a different commit from the checkout.

A fourth workflow keys the same cache, which the M17 entry did not count: lint's clang-tidy job.
The check covers it by the same argument, since it constrains the file the key hashes rather
than any one workflow's key.

## What is not proved

**That no stale cache has ever been restored.** The check prevents the gap from opening; it
cannot say whether it ever did. The records have agreed at every commit this project has
pushed, since the submodule has not been bumped since it was added, so there is nothing to find.
