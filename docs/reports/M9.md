**The one that survived matters more than the twelve that did not.** Recapturing the
before-image on every apply passed the entire suite, because after a revert the scene is back
at the before-image and a second capture takes the same value. The sequence that distinguishes
them is two applies with no revert between — which `History` never does, but `Command` is a
public type and cannot rely on its only current caller's discipline. That gap is now two tests.

## Benchmark impact

**None on the code, and the measurement taught something about the measuring.** M9 added an
editor and panels, none of which runs inside a tick or a draw, so no change was expected.

The first comparison against the `ebb5f03` baseline reported **two regressions**, at 1.29x and
1.80x, both at 102,400 cells. Neither reproduced. Three consecutive clean runs:

| Scenario | Baseline | Three runs | Spread |
|---|---|---|---|
| `simulation/tick cells=102400` | 0.161 ms | 0.160, 0.162, 0.163 | 1.02x |
| `simulation/snapshot cells=102400` | 0.136 ms | 0.134, 0.134, 0.134 | 1.00x |

The first run was taken immediately after a release build and two container runs, on a machine
that had not gone quiet. **The 1.25x threshold caught load, not a regression** — which is the
false positive the threshold's own justification predicted would be rare, observed once.
`docs/PERFORMANCE.md` now says to run a comparison on an idle machine, because "profile-guided
changes only" is worth nothing if the profile is of the build system.

The same runs turned up something in the baseline itself. `simulation/snapshot` at 1,048,576
cells is recorded as 1.876 ms and measures 1.406 to 1.513 ms across three clean runs, about 20%
faster and consistently so. Nothing in M9 touched the snapshot path, so the likely explanation
is the reverse of the above: that entry was recorded while the machine was busy. It is left
alone rather than quietly re-recorded — a baseline is not re-recorded to make a number look
better, and a comparison that is 20% *faster* than its baseline harms nothing. It is noted here
so the next person to see it does not go looking for an optimisation that never happened.

Two costs were considered and kept small by design rather than measured after the fact. The log
console copies the record buffer only when its push count changes, so a frame in which nothing
was logged does one locked integer read instead of copying and allocating per record. The
position widget emits no command when the value has not changed, so resting a pointer on the
field does not fill the undo stack.

## Remaining risks

1. **The renderer has run on one graphics processor and one software rasteriser.** Direct3D 12
   and non-Apple hardware are unverified. This is the largest untested surface in the project
   and CI on the current runners does not reduce it. Unchanged by M9 and not addressable by it.
2. **The drag widget has no automated test.** Driving a Dear ImGui control programmatically
   needs synthetic pointer input at precise coordinates and would test the harness more than the
   panel. Everything either side of it is tested: the commands and history headlessly, the
   filter logic headlessly, the panel's render path under the `gpu` label on two backends. The
   widget itself was verified by hand and by captured frames, and this report says so rather
   than implying coverage that does not exist.
3. **`edit::History` assumes it is the scene's only writer.** The sandbox's demo animation is a
   deliberate exception and is documented as one, and pausing it is why `Space` exists. A second
   undocumented writer would make undo restore stale state. The failure is loud rather than
   silent — a failed revert clears the history and logs — but the contract is enforced by
   documentation, not by the compiler.
4. **Panel layout is verified by eye.** Two defects this milestone were found only by looking at
   captured frames: a display-mode button running off the panel edge, and two panels defaulting
   into the same band. Nothing tests layout, and nothing reasonably could at this cost.

## The next smallest slice

There is no next milestone queued; see the roadmap's "After M9". Of the work that is ready to
start, the smallest genuinely useful slice is:

**A `platform::TextInput` event and character forwarding in `DebugUi`, then the rename widget.**
It is small and self-contained: handle `SDL_EVENT_TEXT_INPUT` in `platform.cpp`, add the event
to the variant, call `io.AddInputCharactersUTF8` in `DebugUi::handle_event`, and give the
inspector an `InputText` that emits the `edit::Rename` command, which already exists and is
already tested. It closes the one stated limitation on M9's first exit criterion.

Two larger items are **owner decisions, not engineering ones**, and neither should be started
without one: hashing in parallel, which is the largest measured performance win left at roughly
40% of the tick but spends `kHashAlgorithmVersion` 3 and invalidates every save and replay; and
embedded scripting, deferred by ADR-0009 behind a trigger that is a limitation somebody hits
rather than a date.
