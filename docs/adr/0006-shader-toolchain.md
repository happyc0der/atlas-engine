# 0006 — Shader toolchain

## Status

Accepted, 2026-09-15.

## Context

SDL_GPU accepts compiled shaders, and which format depends on the backend: SPIR-V for
Vulkan, Metal Shading Language or a precompiled `.metallib` for Metal, and DXBC or DXIL for
Direct3D 12. Atlas must therefore author shaders once and produce several outputs.

The obvious answer is SDL_shadercross, which exists precisely for this and also handles the
per-backend resource binding conventions that SDL_GPU requires. It cannot be used here. It
depends on Microsoft's DirectX Shader Compiler, and DXC supports Windows and Linux x86_64
only: the vcpkg port that supplies it declares exactly that, and Microsoft publishes no
macOS build. The development machine for this project is an Apple Silicon Mac. Building DXC
from vendored sources is possible, and SDL_shadercross's own continuous integration does it,
but it is a long build of a large compiler to obtain a tool that the one machine doing the
work would then have to rebuild on every toolchain change.

There is a second constraint. The machine has Command Line Tools rather than full Xcode, so
there is no `metal` compiler and no way to produce a `.metallib` at all.

## Decision

**HLSL is the authoring language.** One source per shader stage, in
`assets/source/shaders/<name>.<vert|frag>.hlsl`.

**The route is glslang then SPIRV-Cross.** `glslang -D` compiles HLSL to SPIR-V;
`spirv-cross --msl` translates SPIR-V to Metal Shading Language. Both tools are
cross-platform, both are in the pinned vcpkg baseline, and both install from Homebrew or apt
in seconds. `tools/cook_shaders.py` drives them.

**Metal shaders ship as MSL source**, which SDL compiles when the device is created. This is
what makes the absent Metal compiler a non-issue rather than a blocker.

**Cooked outputs are committed**, together with a manifest recording each source's hash and
the entry point for each format. Building and running Atlas therefore needs no shader
toolchain; only changing a shader does. `tools/cook_shaders.py --check` recompiles into a
temporary directory and compares, which is what continuous integration runs, and which turns
"someone forgot to re-cook" into a failed build rather than a stale triangle.

**Entry points are recorded rather than assumed.** SPIRV-Cross renames the entry point to
`main0`. Discovering that by guessing costs an afternoon, so the manifest states it and the
loader reads it.

**Direct3D 12 is deferred.** Without DXC there is no DXIL, so Atlas ships SPIR-V and MSL
only. On Windows that means the Vulkan backend rather than Direct3D 12. This is a real
limitation, recorded here rather than discovered later: it is revisited when either a
Windows machine joins the project, at which point DXC runs there and a continuous-integration
job can produce DXIL into the same committed outputs, or DXC gains a macOS build.

## Alternatives

**SDL_shadercross, built from vendored sources on macOS.** The most complete answer: it
handles the binding conventions and emits every format. Rejected for M2 because of the DXC
build, and because the binding conventions it exists to handle do not apply to a shader that
reads nothing. It is the leading candidate to revisit at M3, when uniforms and textures make
those conventions matter.

**Slang.** Ships macOS arm64 binaries, compiles an HLSL-like language, and emits SPIR-V and
Metal directly. A real option, and the fallback named in the Gate 0 plan. Rejected because it
introduces a new shading language dialect and a dependency outside the vcpkg baseline, to
solve a problem that two tools already in the baseline solve.

**Author GLSL instead of HLSL.** glslang's native input, so one less translation. Rejected
because HLSL is what SDL_GPU's documentation and examples use for its binding conventions,
and diverging from that would make every future binding question harder to answer.

**Compile shaders at runtime.** No build step and no committed artifacts. Rejected: it puts a
compiler in the shipping application, makes a shader error a runtime failure, and the
specification requires shaders to be build outputs.

## Consequences

- The toolchain installs in seconds on all three platforms and needs no vendored compiler.
- A contributor with no shader tools can still build, run, and test Atlas.
- Windows uses the Vulkan backend, not Direct3D 12, until DXIL can be produced.
- Resource binding conventions are unaddressed. The first triangle reads nothing, so nothing
  needs binding; M3 must settle it, either by replicating SDL's remapping with SPIRV-Cross
  flags or by adopting SDL_shadercross after all. This ADR is likely to be superseded then.
- Committed binary outputs mean shader changes show up as binary diffs, and a stale commit is
  possible. The `--check` mode is the guard.

## Rollback cost

Low. The cooking tool is one script, the outputs are regenerated by running it, and the
runtime only ever sees bytes plus an entry-point name. Switching to SDL_shadercross or Slang
changes `tools/cook_shaders.py` and the committed outputs, and nothing in the engine.
